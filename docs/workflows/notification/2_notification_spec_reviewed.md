## 1. 검토 요약
전반적으로 SIEM 환경에 필요한 핵심 알림 기능을 잘 정의하고 있습니다. 특히 복잡한 인덱스 구조를 지양하고 규칙 내에 Webhook 설정을 통합함으로써 구현의 단순성과 관리 효율성을 높인 점이 긍정적입니다. 팝업을 제외하고 상위 서비스로 이관한 결정은 시스템 간 역할 분담(Separation of Concerns) 관점에서 적절합니다.

---

## 2. 상세 검토 의견

### 2.1 기술적 타당성 (Technical Feasibility)
- **배치 엔진 (1분 주기):** FastAPI의 `BackgroundTasks` 또는 전용 스케줄러를 사용하여 충분히 구현 가능합니다. 다만, 규칙이 많아질 경우 OpenSearch에 가해지는 쿼리 부하를 고려하여 규칙별 실행 시점을 분산시키는 로직이 필요할 수 있습니다.
- **Webhook 발송:** 비동기 HTTP 클라이언트(httpx 등)를 사용하여 알림 생성과 동시에 Webhook 발송을 병렬로 처리할 수 있어 성능상 큰 문제가 없을 것으로 판단됩니다.
- **데이터 모델:** OpenSearch의 `object` 타입을 활용한 `condition_config` 설계는 다양한 검색 조건(Count, Pattern 등)을 유연하게 수용할 수 있는 적절한 선택입니다.

### 2.2 잠재적 문제점 및 개선 제안 (Missing Items)
1. **Webhook 실패 처리 (Retry Logic):** 외부 시스템의 장애로 인해 Webhook 전송이 실패할 경우에 대한 재시도 정책이 누락되어 있습니다. `cs_notifications`에 전송 실패 상태를 기록하거나, 재시도 횟수를 제한하는 로직이 필요합니다.
2. **알림 폭주 제어 (Throttling):** 동일한 조건으로 너무 빈번하게 알림이 발생할 경우(예: 초당 수백 개의 로그 매칭), 시스템 부하 및 사용자 피로도를 줄이기 위한 '알림 중복 방지' 또는 '발생 주기 제한' 기능이 필요할 수 있습니다.
3. **Webhook 데이터 포맷:** 외부 시스템이 이 알림을 수신할 때 사용할 공통 JSON 스키마를 정의해야 합니다. (알림 시간, 등급, 발생 규칙, 원본 데이터 링크 등 포함)

### 2.3 UI/UX 검토
- **스낵바(3초):** 중요한 알림을 놓치지 않도록 스낵바에 '목록 바로가기' 버튼이나 '닫기' 버튼을 포함하는 것을 권장합니다.
- **읽음 처리:** 대량의 알림이 발생할 경우를 대비하여 '전체 읽음 처리' 기능이 목록 페이지에 포함되어야 합니다.
