## 1. 개요

### 1.1 목적
cruxSIEM에 TOTP(Time-based One-Time Password) 기반 2단계 인증(2FA)을 추가하여 보안 관제 플랫폼의 계정 보안을 강화합니다.

### 1.2 배경
- SIEM 플랫폼은 민감한 보안 로그 및 이벤트 데이터를 다루므로 계정 탈취 시 피해가 큼
- 폐쇄망(내부망) 환경에서도 동작해야 하므로 외부 서버 의존 없이 구현
- Google Authenticator, Microsoft Authenticator 등 범용 TOTP 앱과 호환되는 RFC 6238 표준 사용
- 기존 로그인 플로우(이메일/비밀번호)에 OTP 검증 단계를 추가

### 1.3 범위

**포함:**
- 사용자별 OTP 등록 (QR코드 스캔)
- OTP 활성화/비활성화
- 로그인 시 OTP 검증 단계 추가
- 백업 코드 발급 (OTP 앱 분실 시 대체)
- 관리자에서 전체 OTP 강제 활성화 정책 설정
- 폐쇄망 완전 지원 (외부 통신 없음)

**제외:**
- SMS/이메일 OTP (TOTP 앱 방식만 지원)
- Push 알림 방식 인증
- FIDO2/WebAuthn (향후 고려)
- OTP 앱 직접 배포

## 2. 요구사항

### 2.1 기능 요구사항

#### 필수 기능 (Must Have)
1. TOTP 시크릿 키 생성 (pyotp.random_base32)
2. QR코드 생성 (서버에서 직접 생성, 외부 API 불사용)
3. OTP 코드 검증 (±1 window, 30초 슬롯)
4. OTP 활성화 플로우 (QR스캔 → 코드 입력 → 확인)
5. 로그인 2단계: 이메일/비밀번호 통과 후 OTP 코드 입력 화면
6. 백업 코드 발급 (8자리 코드 8개, 1회성)
7. 관리자 설정: 전체 사용자 OTP 필수 여부 토글
8. 사용자 마이페이지: OTP 등록/해제 UI

#### 선택 기능 (Should Have)
1. OTP 등록 완료 시 이메일 알림 (폐쇄망이면 내부 SMTP)
2. OTP 인증 실패 횟수 제한 (5회 실패 시 계정 잠금)
3. 신뢰 디바이스 등록 (30일간 OTP 생략)

#### 향후 고려사항 (Nice to Have)
1. FIDO2/WebAuthn 지원
2. OTP 인증 이력 조회

### 2.2 비기능 요구사항

#### 성능
- QR코드 생성 응답 시간: 500ms 이내
- OTP 검증 응답 시간: 200ms 이내

#### 보안
- 시크릿 키는 AES-256 암호화 후 OpenSearch 저장
- 시크릿 키는 절대 응답 본문에 평문 노출 금지 (QR코드 이미지만 제공)
- 백업 코드는 bcrypt 해싱 후 저장, 사용 즉시 폐기 (1회성)
- OTP 검증은 timing-safe compare 사용

#### 폐쇄망 호환성
- QR코드 생성: `qrcode[pil]` 라이브러리 (서버 자체 생성)
- TOTP 알고리즘: `pyotp` 라이브러리 (외부 통신 없음)
- Google Authenticator 앱은 초기 설치 후 오프라인 동작

#### 시간 동기화
- 서버-클라이언트 폰 간 시간 차이 허용 범위: ±60초 (window=2)
- 내부 NTP 서버 설정 권장사항 문서화

## 3. 사용자 시나리오

### 3.1 주요 사용자
- cruxSIEM 모든 사용자 (admin, monitoring, approver, user)

### 3.2 사용 시나리오

#### 시나리오 1: OTP 최초 등록
**사전 조건:**
- 사용자가 로그인된 상태
- OTP 미등록 상태

**실행 단계:**
1. 사용자가 [마이페이지] → [보안 설정] → [2단계 인증 등록] 클릭
2. 서버에서 TOTP 시크릿 키 생성 및 QR코드 이미지 반환
3. 사용자가 Google Authenticator 앱으로 QR코드 스캔
4. 앱에서 생성된 6자리 OTP 코드 입력
5. 서버에서 코드 검증 성공 시 OTP 활성화
6. 백업 코드 8개 화면 표시 (1회만 표시, 저장 권고)

**기대 결과:**
- OTP 활성화 완료
- 다음 로그인부터 OTP 코드 요구

**예외 상황:**
- OTP 코드 불일치 → "인증 코드가 올바르지 않습니다" 표시
- 시간 동기화 문제 → "서버와 시간 차이가 너무 큽니다" 안내

---

#### 시나리오 2: OTP 활성화 후 로그인
**사전 조건:**
- 사용자가 OTP 등록 완료 상태

**실행 단계:**
1. 이메일/비밀번호 입력 후 1차 인증 통과
2. 서버에서 `otp_required: true` 응답 반환 (토큰 미발급)
3. 프론트엔드에서 OTP 코드 입력 화면으로 전환
4. 사용자가 TOTP 앱에서 6자리 코드 입력
5. 서버에서 코드 검증 후 최종 JWT 토큰 발급
6. 대시보드로 이동

**기대 결과:**
- 2단계 인증 통과 후 정상 로그인

**예외 상황:**
- 코드 만료 → "코드가 만료되었습니다. 앱에서 새 코드를 확인하세요"
- 연속 5회 실패 → 계정 잠금 처리

---

#### 시나리오 3: 백업 코드로 로그인
**사전 조건:**
- 사용자가 OTP 앱에 접근 불가 (폰 분실 등)

**실행 단계:**
1. OTP 입력 화면에서 "백업 코드 사용" 클릭
2. 발급받은 8자리 백업 코드 입력
3. 서버에서 검증 후 해당 백업 코드 폐기
4. 로그인 성공, OTP 재등록 안내 표시

**기대 결과:**
- 백업 코드로 로그인 성공
- 사용한 백업 코드는 즉시 폐기

---

#### 시나리오 4: 관리자 OTP 강제 정책
**사전 조건:**
- 관리자가 로그인된 상태

**실행 단계:**
1. 관리자 [설정] → [보안 정책] → [OTP 필수 활성화] 토글
2. 토글 ON 시 OTP 미등록 사용자 로그인 시 OTP 등록 강제 유도

**기대 결과:**
- 미등록 사용자가 로그인하면 OTP 등록 페이지로 리디렉션

## 4. 데이터 요구사항

### 4.1 OpenSearch 인덱스 변경

#### cs_users (기존 필드 추가)
| 필드명 | 타입 | 필수 여부 | 설명 |
|-------|------|----------|------|
| otp_enabled | boolean | Y | OTP 활성화 여부 (기본: false) |
| otp_secret_enc | keyword | N | AES-256 암호화된 TOTP 시크릿 키 |
| otp_backup_codes | keyword[] | N | bcrypt 해싱된 백업 코드 목록 |
| otp_enrolled_at | date | N | OTP 등록 일시 |

#### cs_settings (기존 인덱스 — 보안 정책 필드 추가)
| 필드명 | 타입 | 필수 여부 | 설명 |
|-------|------|----------|------|
| otp_required | boolean | Y | 전체 OTP 강제 활성화 여부 (기본: false) |

### 4.2 임시 세션 (OTP 검증 대기 상태)
- 1차 인증(이메일/비밀번호) 통과 후 OTP 검증 전까지 임시 토큰 발급
- 임시 토큰은 5분 유효, OTP 검증 성공 시 정식 JWT로 교체
- cs_sessions에 `otp_verified: boolean` 필드 추가

## 5. API 요구사항

### 5.1 신규 엔드포인트

#### API 1: OTP 등록 시작 (QR코드 발급)
- **Method:** POST
- **Path:** /api/v1/auth/otp/enroll
- **설명:** TOTP 시크릿 키 생성 및 QR코드 이미지 반환
- **헤더:** Authorization: Bearer {token}
- **응답 (200 OK):**
  ```json
  {
    "qr_code_image": "data:image/png;base64,iVBOR...",
    "manual_key": "JBSWY3DPEHPK3PXP"
  }
  ```
- **보안:** 시크릿 키는 DB에 암호화 저장, 응답에는 수동 입력용 표시

#### API 2: OTP 활성화 확인
- **Method:** POST
- **Path:** /api/v1/auth/otp/verify-enroll
- **설명:** QR코드 스캔 후 첫 코드 입력으로 OTP 활성화 확정
- **요청:**
  ```json
  { "code": "123456" }
  ```
- **응답 (200 OK):**
  ```json
  {
    "backup_codes": ["ABCD1234", "EFGH5678", "..."]
  }
  ```

#### API 3: OTP 코드 검증 (로그인 2단계)
- **Method:** POST
- **Path:** /api/v1/auth/otp/verify
- **설명:** 로그인 2단계에서 OTP 코드 검증 후 JWT 토큰 발급
- **헤더:** Authorization: Bearer {임시토큰}
- **요청:**
  ```json
  { "code": "123456" }
  ```
- **응답 (200 OK):**
  ```json
  {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "token_type": "bearer",
    "expires_in": 86400
  }
  ```

#### API 4: 백업 코드 검증 (로그인 2단계 대체)
- **Method:** POST
- **Path:** /api/v1/auth/otp/verify-backup
- **헤더:** Authorization: Bearer {임시토큰}
- **요청:**
  ```json
  { "backup_code": "ABCD1234" }
  ```
- **응답:** OTP 검증 API와 동일

#### API 5: OTP 비활성화
- **Method:** DELETE
- **Path:** /api/v1/auth/otp
- **헤더:** Authorization: Bearer {token}
- **요청:** 현재 OTP 코드 or 백업 코드 확인 후 비활성화
  ```json
  { "code": "123456" }
  ```
- **응답 (204 No Content)**

### 5.2 기존 엔드포인트 수정

#### 로그인 API (POST /api/v1/auth/login) 응답 변경
- OTP 등록 사용자의 경우:
  ```json
  {
    "otp_required": true,
    "temp_token": "임시토큰 (5분 유효)",
    "user": { "id": "...", "name": "..." }
  }
  ```
- OTP 미등록 사용자는 기존 동일

## 6. UI/UX 요구사항

### 6.1 신규 화면

#### OTP 등록 화면 (마이페이지 내 모달 또는 전용 페이지)
- QR코드 이미지 표시
- "앱에서 QR코드를 스캔한 후 생성된 6자리 코드를 입력하세요" 안내

- "보안 앱에서 6자리 코드를 확인하세요" 안내

- "백업 코드 사용" 링크
- "이전으로 (1단계로 돌아가기)" 링크

#### 관리자 보안 정책 설정 (관리자 설정 탭)
- "OTP 2단계 인증 필수" 토글 스위치

- 로그인 플로우: 1단계(이메일/비밀번호) → 2단계(OTP 코드) 분기 처리
- 마이페이지 보안 설정 탭: OTP 등록/해제 버튼 추가

## 7. 제약사항 및 고려사항

### 7.1 기술적 제약사항
- 서버와 사용자 폰의 시간이 ±60초 이상 차이나면 OTP 검증 실패 가능
- pyotp 라이브러리 의존 (Python 3.8+)
- QR코드 생성에 Pillow 라이브러리 필요 (이미지 처리)
- 시크릿 키 암호화에 cryptography 라이브러리 필요

### 7.2 폐쇄망 고려사항
- 모든 QR코드 생성 및 TOTP 검증은 서버 자체 처리 (외부 통신 없음)
- Google Authenticator 앱은 설치 후 인터넷 없이 동작
- 내부 NTP 서버로 시간 동기화 권장

### 7.3 기존 시스템 영향
- 로그인 API 응답 구조 변경 → 프론트엔드 로그인 플로우 수정 필요
- cs_users 인덱스에 OTP 관련 필드 추가 (기존 데이터 영향 없음)

## 11. 질문 및 미결정 사항

1. OTP 강제 정책 적용 시 기존 미등록 사용자 처리 방법?
   > 로그인 시 OTP 등록 페이지로 강제 리디렉션, 등록 전까지 다른 페이지 접근 불가
2. 시크릿 키 암호화 키 관리 방법?
   > 환경변수 OTP_ENCRYPTION_KEY로 관리 (ASSISTANT.md에 추가 필요)
3. 신뢰 디바이스 기능 포함 여부?
   > 추후 결정 (현재 스코프 제외)
4. 관리자가 특정 사용자의 OTP를 강제 해제할 수 있어야 하는가?
   > 관리자가 otp 비활성화하면 그냥 id/pwd 로그인으로 진행
5. OTP 인증 이력을 별도 인덱스에 기록해야 하는가?
   > cs_login_attempts 에 otp 여부만 불린으로 넣으면 됨
